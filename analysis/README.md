## The results in one table

See `headline.md` (generated). Readout:

- **Graviton5 leads per $ vs x86 in every CPU-bound class**: Go 1.97x, Java 1.80–2.11x,
  inference 1.96–2.36x, MongoDB 1.36–1.39x, PostgreSQL 1.06–1.09x (a raw tie, so "same
  speed, cheaper"). Against AMD it leads per $ everywhere except PostgreSQL (0.70x).
- **AMD wins PostgreSQL clearly**: ~1.8x raw, ~1.5x per $. Show it openly.
- **Ties (the two days overlap)**: Java tuned and vthreads arm = amd (raw; arm still wins
  per $ because m9g is ~20 % cheaper); PostgreSQL arm = x86; MongoDB amd = x86.
- **x86 (m8i) is last on raw throughput everywhere except PostgreSQL** (where it ties arm).
  Root fact: at 4xlarge it is 8 cores + SMT, while m8a and m9g are 16 physical cores
  (`facts-setup.md` §1).
- **Network**: throughput = the instance cap (m9g 16.9 Gbps, m8a/m8i 14.9). The "tuned"
  latency knob (IRQ pinning, adaptive-rx off) roughly doubles CPU per Gbps: arm 0.029 → 0.064,
  amd 0.037 → 0.079, x86 0.088 → 0.106 cores/Gbps (d2 only).
- **Day-to-day drift** 0–8 % per cell; no ranking flipped between instances except within ties.

## Facts verified while assembling (2026-09-28)

- **llama.cpp threads.** "stock" = llama.cpp's default thread count, on purpose (overlay
  comments): 16 on m9g/m8a, 8 on m8i (physical cores only, SMT siblings idle). "tuned" = `-t 15`
  on every chip (the pod's 15 exclusive vCPUs). On x86, `-t 15` over 8 threads is +18 % in Task 7 (x86-t8 47.6 vs x86-tuned 56.3, d2) — the
  stage number; calibration (n=1) had read +42 %. Source-verified: at b10775
  `common_cpu_get_num_math()` counts the host's physical cores and ignores the pod cpuset.
  The `n_threads = 16` recorded on arm-tuned is the runner's probe, not the server.
- **Inference arm-tuned d1 = 100 vs d3 = 108 tok/s**: the ledger records the d1 spread as
  unexplained. Do not call it a noisy node on stage.
- **Nothing needed from the live cluster**: per-run results, APerf system info per node,
  flamegraphs and the final inventory are on disk; CloudWatch and Cost Explorer are
  account-level. A destroy would only lose the 3 EBS volumes (PG + Mongo datasets,
  reproducible; Pyroscope raw store, 20 GB — snapshot it if a destroy happens).

## Before any number reaches a slide

1. **Fairness caveats to say out loud**
   - llama.cpp image: AMX kernels on Xeon; on Graviton the Arm i8mm repack kernels are on,
     only the KleidiAI path is off (b10775 defaults). Metric = generation tok/s; for prompt
     processing x86 wins big (Spare Cores: m8a/m8i ~2.5x m9g).
   - Mongo is not CPU-bound at the knee.
   - One node per cell per day, one region/AZ, on-demand prices only.
2. **x86-smtoff is not a single-variable comparison**: it also carries the full JIT bundle
   that x86-tuned doesn't (`facts-setup.md` open question 1). Compare it with care or caveat it.
3. **Flamegraphs**: only Java profiles are complete. Inference/PostgreSQL eBPF profiles
   have kernel frames only (no user stacks) — not slide material. The APerf counters are the
   "why" layer for the rest (IPC, MPKI; only IPC, branch-MPKI, L1i-MPKI and frontend stalls
   exist on all three chips).
4. **Stale text to fix** (details in `facts-history.md` last section and `facts-setup.md`
   open questions): spec says PG fixed runs at 2x clients, Java tuned same flags on both
   archs, loader c7i.4xlarge, "AMD out of scope", voseo at spec:164; CLAUDE.md says the
   cluster is destroyed between lab days.
5. **Framing changed by the data**: Go was planned as "the chip barely matters" — it is
   1.8x arm vs x86. The abstract says "Ollama"; the lab ran llama.cpp server.
6. **Statistics**: `stats.md` (bootstrap over days then runs, plus the min–max envelope;
   n=2 days makes the interval weak, the envelope decides "within noise").
